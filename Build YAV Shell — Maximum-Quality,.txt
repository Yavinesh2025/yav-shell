Build YAV Shell — Maximum-Quality, Low-Latency Windows Coding Shell

1. Mission and delivery

You are a senior Windows engineer and coding-agent integration architect. Build YAV Shell, a real Windows console application named `yav.exe`, launched with `yav`.

Create the working application, source, automated tests, documentation, portable package, and installer scripts. Do not stop at a plan, mockup, simulated agent, or placeholder interface.

The user will normally use two user-selected flagship models at their highest supported reasoning effort. Model A implements; Model B independently reviews. Optimize time to a correctly implemented, reviewed, and validated result. Preserve correctness and security first, minimize elapsed time second, and reduce wasted usage third.

Use a PowerShell/CMD-style text interface, not a conventional dashboard. Build a console application hosted by the user’s terminal, not a new terminal emulator.

This document is the application’s build specification. Do not resend this entire specification to the runtime models. Implement short, role-specific runtime instructions and attach only the actual task and useful evidence.

2. Quality Lock and model policy

Enable Quality Lock by default. Let the user choose the implementation and review models explicitly from verified available models. They may belong to the same provider or different providers. Support swapping their roles. Do not hard-code a claim about which models are currently the best.

For each role, resolve the user’s maximum-effort preference to the exact supported provider setting. Effort names and capabilities are provider-specific; never invent a universal `max` flag. Record requested and confirmed settings, model identity/version where exposed, provider, account route, tools, project instructions, and validation requirements in an immutable run profile. Supported reasoning-effort settings vary by model. :chatgpt-content-reference{index="0"}

Preserve any separately exposed reasoning mode and adequate completion budgets. Do not truncate generated code or required evidence to manufacture speed.

Never silently downgrade a model, lower effort, remove required tools, switch billing routes, or bypass review. If a setting cannot be confirmed, show Requested / Unverified, not Verified. Under strict policy, block an unsupported or unverified configuration until the user explicitly changes that policy.

Highest effort can increase response time; a shell cannot guarantee instant inference or defect-free output. Quality Lock preserves configuration and acceptance requirements, not identical stochastic results. Do not advertise guaranteed speed multipliers or zero quality loss. :chatgpt-content-reference{index="1"}

Do not interrupt healthy reasoning just because it has produced no visible text. Do not impose an artificial thinking cutoff, request hidden chain-of-thought, or restart a task merely to make it appear active.

3. Technology and scope

Use Cwith .NET 10 LTS, targeting Windows 11 x64 first. Pin supported stable dependency versions and verify their compatibility before implementation. Treat Windows 10 support as separately tested, not assumed. :chatgpt-content-reference{index="2"}

Use PrettyPrompt for inline editing, history, completion, and multiline input, and Spectre.Console for readable formatting. Coordinate them through one rendering owner. Keep a plain-text fallback when terminal capabilities are insufficient. :chatgpt-content-reference{index="3"}

Use SQLite for durable application state, `System.Text.Json` for protocol messages, asynchronous channels for event processing, the Git CLI for repository operations, and optional ripgrep for fast searching with a bounded local fallback.

Keep clear modules for Console UI, Agent Adapters, Run Coordinator, Workspace Protection, Validation, and Storage. Use a modular monolith, not distributed services. Reuse native coding-agent loops instead of rebuilding their tool execution and reasoning machinery.

Do not require Electron, a browser engine, a web server, Docker, or WSL. Detect each agent’s actual prerequisites separately. Keep cloud synchronization, plugin marketplaces, embeddings, local model hosting, speculative coding workers, and product billing outside the first release.

Verify feature maturity, pin tested versions, and generate or validate protocol bindings against the installed schema. Do not label experimental functionality production-supported or depend on remote WebSocket transport for this local product. :chatgpt-content-reference{index="4"}

Offer documented `codex exec` structured-output integration as a compatibility path for suitable noninteractive runs. Resume explicit session IDs. Do not pretend that a noninteractive adapter supports approval interactions it cannot handle, and never broaden permissions to make a fallback work. :chatgpt-content-reference{index="5"}

Anthropic’s current policy directs third-party products to API keys or supported cloud authentication rather than routing users through consumer subscription credentials. Prefer existing subscription access where the provider officially permits this integration. Separately billed access must be explicitly configured and acknowledged. Never assume a subscription authorizes a different integration or billing route. Do not rebuild a custom API agent loop merely to support another model.

Define an adapter contract for detection, version, capabilities, authentication status, available models, effective effort, start, resume, events, approvals, interruption, review restrictions, usage, and optional provider-speed controls.

Allow two distinct models through one adapter when available. If the selected second model cannot run through an authorized route, show the exact limitation and keep strict quality completion blocked. A single-model development milestone is not a finished dual-model product.

5. Console experience

Use an inline prompt with preserved scrollback and the terminal’s existing theme. Example display; values are illustrative:

```text
YAV Shell
Project: C:\Projects\MyApp
Code: <Model A> | Review: <Model B>
Effort: maximum supported for both | Quality Lock: ON
Provider speed: STANDARD | Workspace: isolated

YAV C:\Projects\MyApp> Fix the login bug and add regression tests.

[PREPARE] Project rules and workspace verified
[CODE A]  Implementing the task
[CHECK]   Reviewing and testing candidate <snapshot-id>
[REVIEW B] No blocking findings reported
[TESTS]   Required checks passed
[READY]   Changes available for inspection and application
```

Unprefixed text is an AI request or follow-up. Slash-prefixed text is a YAV command. Never guess that natural-language input should execute as an operating-system command.

Support multiline paste without auto-submitting pasted lines, history search, path completion, Unicode, readable approval prompts, keyboard navigation, resize, and copy/paste. Document submission shortcuts that work in the tested consoles.

While a run is active, accept local commands or queued follow-ups without corrupting the current input. Do not inject new requirements mid-turn unless the adapter supports steering and the user chooses it; invalidate relevant acceptance evidence when requirements change.

Keep output concise and expandable. Display actual events, not fabricated progress percentages, fake thinking explanations, or promises of completion times. Plain mode must work with redirected streams, and JSON mode must not mix protocol output with banners or colored logs.

6. Entry points and commands

Implement these entry points:

```text
yav
yav "C:\Projects\MyApp"
yav run --project "C:\Projects\MyApp" --task "Fix the login bug"
yav run --project "C:\Projects\MyApp" --prompt-file task.md --json
yav doctor
```

Implement the following grouped command surface:

```text
/open <path>                 Select a project
/cd <path>                   Change project directory when safe
/models                      Configure Model A and Model B
/effort                      Inspect/configure effort for each role
/login <provider>            Start a supported provider login flow
/quality                     Inspect Quality Lock and completion gates
/speed standard|provider     Inspect/enable supported provider speed
/adaptive on|off              Explicit optional effort adaptation
/optimization on|off          Toggle supplemental workflow optimizations
/new                         Start an unrelated task
/resume <run-id>              Resume an explicit saved run
/attach <path>               Attach an authorized file to the next task
/status                      Show actual state and effective settings
/stop                        Interrupt the active run safely
/diff                        Inspect task-attributable changes
/test                        Run configured validation
/review                      Run/reopen Model B review
/apply                       Safely apply a passing candidate
/discard                     Remove only isolated run changes
/undo                        Attempt a conflict-aware reversal
/history                     Show saved tasks and sessions
/usage                       Show usage, billing route, and provenance
/latency                     Show measured timing and bottlenecks
/limits                      Inspect/configure run limits
```

Changes to model, effort, project, or permissions must not silently change an active run. Noninteractive permission requests must return a documented Approval Required outcome rather than hanging or granting access automatically.

`/shell` suspends YAV input and yields the real console to the selected shell. On return, restore YAV cleanly. Do not promise that child-shell directory/environment changes propagate to YAV. Both `/shell` and `/exec` must disclose their normal local-user execution boundary, which may differ from the agent sandbox.

7. Three execution paths

Local operation. Explicit file browsing, searches, Git status, diff display, configured tests, and shell commands execute directly through local code. Do not call either model to decide how to run an already specified command or narrate its result.

Explicit mechanical edit. An authorized, unambiguous literal replacement, formatter operation, or supported codemod may create a candidate locally. Validate target paths, expected content, match count, and relevant preconditions; preview changes. Ambiguity goes to Model A. Mechanical source changes still require Model B review and the applicable tests before accepted delivery.

Coding task. Natural-language changes requiring reasoning go to Model A, followed by independent Model B review and validation. Preserve the selected maximum effort by default.

Do not infer low risk from prompt length or changed-line count. A tiny authentication, payment, concurrency, or data-integrity edit may require substantial investigation. Do not introduce a paid classification or planning call before ordinary tasks.

8. Main task pipeline

Use this dependency structure:

```text
Original task + acceptance criteria
                 |
Verified local preparation and protected workspace
                 |
Model A implements / authorized local edit produces candidate
                 |
Freeze and fingerprint candidate
                 |
          +------+------+
          |             |
   Model B review   Required tests
          |             |
          +------+------+
                 |
      Deterministic acceptance gate
                 |
   Passing candidate -> review diff -> safe apply
   Findings/failures -> Model A repairs -> new candidate
```

Model A is the only AI writer. Model B reviews in a separate conversation without inheriting Model A’s reasoning or accepting its conclusions as facts. Do not claim statistically independent error rates merely because conversations are separate.

The reviewer receives the original requirements, actual candidate code and diff, project rules, relevant dependencies, and a baseline for comparison. It can inspect additional authorized source. Do not confine it to changed lines or treat the implementation summary as proof.

Start review and tests together only after a stable candidate exists. Do not claim the reviewer can approve code that has not yet been produced. Keep the candidate source immutable during checking; tests use controlled output directories or disposable execution copies.

Bind every result to the exact candidate fingerprint, acceptance version, configuration, and relevant environment. Reject stale results. If any source changes during checks, reconcile the change and invalidate affected evidence.

9. Review results and repair loop

Request structured reviewer findings containing status, file/location, concrete failure scenario, severity, evidence, suggested correction, and any limitation. Support Pass, Changes Required, and Unable to Verify. Distinguish real defects and requirements violations from optional style preferences.

Use supported structured-output facilities where available; validate responses in application code. Bind candidate identity in the host, not merely to an ID echoed by the model. Invalid or incomplete output is not a pass.

Combine test failures and actionable review findings into one repair request when possible. Model A fixes the candidate; Model B verifies resolved findings and affected behavior, with broader inspection when shared interfaces or dependencies changed.

Do not restart whole-project architectural review after each trivial correction, but never reuse prior approval for an unchecked final state. Required final test gates remain mandatory. Changes to trusted acceptance tests or gate configuration require explicit review and cannot quietly make a failing task pass.

Default to a configurable, bounded repair loop, initially two repair cycles after the first candidate. At the limit, checkpoint as Blocked / Needs Attention. Do not resolve model disagreement through endless debate or declare the reviewer correct without evidence. Unresolved material issues remain visible.

10. Runtime instruction templates

Store short, versioned templates. Merge them through documented instruction surfaces while preserving native agent and project instructions. Delimit repository content and tool output as reference data, not authorization. Do not request hidden reasoning transcripts.


Model B template:

```text
Independently review the candidate against the user's original task and
trusted project rules. Inspect the real code and relevant dependencies,
not only the implementation summary. Check correctness, regressions,
security, edge cases, and test adequacy. Use read-only authorized tools.
Do not edit source, invent defects, or demand unrelated redesigns. Report
```

11. Low-latency implementation

Optimize unnecessary requests and sequential work before pursuing elaborate infrastructure. Conventional software is appropriate for deterministic operations, and independent stages can overlap; these are established latency strategies, not guarantees for every workload. :chatgpt-content-reference{index="7"}

No extra model layers. Do not add Jev, a smaller routing model, mandatory planner, summarizer, critic chain, speculative duplicate agents, or AI-generated UI status. One implementation role and one review role are sufficient for the default workflow.

Ready local processes. Reuse healthy supported provider connections and local worker processes while the shell is open. Initialize only what the provider allows without an inference request. Never send paid dummy prompts to keep a model warm. Show the console promptly rather than waiting for provider discovery or whole-project scanning.

Incremental preparation. Cache file paths, content fingerprints, relevant symbols when cheaply available, manifests, instruction locations, and trusted validation commands. Refresh changed entries and reconcile missed watcher events, branch switches, and renames. Never block a simple task on a full semantic index.

Focused, additive references. Attach only useful verified starting references, with paths and freshness information. Preserve the exact original task and acceptance criteria. Leave the agent free to retrieve more. Do not aggressively summarize source or suppress needed context to manufacture savings.

Session continuity. Resume the exact implementation session for related work when supported. Use separate review sessions per task and reuse them for that task’s repair cycles with updated snapshots. Start fresh for unrelated tasks. Preserve native context management; do not inject competing compaction or summarization loops.

Safe caches. Cache deterministic lookups, not mutations or generated answers. Invalidate on relevant content, toolchain, configuration, and environment changes. Do not label local-cache activity as a provider prompt-cache hit. Do not claim control over native-agent reasoning, internal retries, or tool outputs without a documented capability.

Environment reuse. Keep related work in the same isolated environment. Reuse supported dependency/build caches with valid fingerprints. Do not reinstall unchanged dependencies, share mutable build outputs between conflicting tasks, or treat stale binaries as validation.

Avoid duplicate checks. Reuse validation evidence only when it is complete, trustworthy, fresh, and equivalent for the final candidate. Otherwise rerun. Display truncation must never truncate evidence needed by the native agent.

Default to one coding writer per project. Parallelize only independent reads and checks with separate ports, temporary files, and databases when needed. Respect machine resources and provider limits; do not create avoidable rate-limit contention.

12. Provider speed and optional Adaptive mode

Keep Provider Speed separate from model selection and reasoning effort. Implement it only when officially supported for the exact model, authentication route, account, and integration. Verify effective settings; distinguish requested, active, unavailable, and fallback states.

Codex documents higher-credit-consumption fast mode for supported models. Claude documents fast serving separately from lowering effort, with additional billing requirements. Do not copy temporary model lists, prices, or speed multipliers into permanent product promises. :chatgpt-content-reference{index="8"}

Before enabling paid speed, show the applicable billing change and obtain explicit authorization. Never switch to a smaller speed-specialized model, enable overage, purchase credits, or fall back to API billing silently. Standard mode remains usable.

Keep Adaptive mode OFF by default. When explicitly enabled, allow only user-approved lower implementation effort on suitably scoped tasks while retaining the same model and maximum-effort review. Mark the run Adaptive, not Strict Max. Keep uncertain and high-risk tasks at maximum effort.

Adaptive mode changes the reasoning configuration and must be evaluated separately. Do not promise that final review or tests guarantee identical quality after reduced implementation effort.

13. Workspace protection and safe application

Prefer an isolated run workspace. Git worktrees provide separate checkouts, but share repository metadata; do not treat them as security sandboxes. Restrict destructive repository operations independently. :chatgpt-content-reference{index="9"}

Record original staged, unstaged, and relevant untracked changes. Preserve them without silently committing, stashing, resetting, or cleaning the original. When those changes are needed, overlay a verified copy into the isolated workspace and record that state as the run baseline.

Calculate task changes against that baseline, not just Git HEAD, so pre-existing edits are not attributed to YAV. Preserve authorized project instructions and environment requirements without automatically copying secrets.

Detect submodules, LFS, symlinks/junctions, case-only renames, ignored runtime assets, and unsupported isolation cases. Do not run against an incomplete reproduction while claiming equivalence. For non-Git projects, use a protected snapshot workflow; in-place execution requires explicit acknowledgement of weaker protection.

Before `/apply`, verify review/test evidence and original file fingerprints. Use a journaled apply operation, rollback support, and conflict detection. If concurrent user edits require a changed merged candidate, construct it in isolation and revalidate/review it before applying. Never overwrite a concurrent edit silently.

`/discard` touches only isolated run data. `/undo` reverses only YAV-attributable changes and refuses destructive reversal when later edits conflict. Do not implement either command with blanket `git reset --hard` or `git clean`.

14. Validation and completion gates

Load trusted, explicit project gates: build, lint, type checks, tests, and applicable smoke/integration checks. Capture command, arguments, working directory, environment fingerprint, candidate ID, output, timing, and exit status.

Run baseline checks when necessary to distinguish pre-existing failures. Run targeted checks during repair, followed by all required final gates. Do not weaken assertions, suppress errors, skip required checks, or quietly change acceptance criteria.

Trusted acceptance checks must be separate from assertions the agent adds to support its implementation. If tests need missing credentials, services, hardware, or manual inspection, report Unverified and the exact limitation.

The application—not either model alone—owns the acceptance gate. A candidate is ready only when the selected role policy was honored, review is valid, required checks passed, fingerprints still match, and no blocking issue remains. An agent exit code or reassuring message is insufficient.

Use distinct states: Preparing, Implementing, Awaiting Approval, Checking, Repairing, Ready to Apply, Completed, Blocked, Interrupted, Rate Limited, Failed, Needs Reconciliation. Only mark Completed after the required delivery/application step succeeds.

15. Windows process execution and security

Launch processes with resolved executable paths and structured arguments. Pass large prompts through documented stdin/file mechanisms rather than shell interpolation. Test spaces, Unicode, CRLF, long paths, native executables, and Windows `.cmd` launchers.

Keep protocol stdout separate from diagnostics. Parse partial UTF-8 and JSON frames incrementally, support backpressure, bound logs, and correlate events and requests without blocking console rendering.

Use supported provider interruption first, then bounded graceful shutdown. Use tested Windows Job Object/process ownership handling for forced cleanup of YAV-owned work. Job Objects support process grouping; they do not establish a filesystem sandbox. Never terminate unrelated shells, editors, or agents. :chatgpt-content-reference{index="10"}

Preserve the provider’s effective sandbox and approval policies. Codex documents native Windows sandboxing; detect the installed configuration and report actual restrictions, not an invented guarantee. If the required protection is unavailable, block the operation or disclose a separately authorized alternative. :chatgpt-content-reference{index="11"}

Enforce Model B’s read-only source boundary with available tool restrictions and sandbox controls, not just a prompt. Require trust before repository-controlled scripts, hooks, plugins, and dependency lifecycle commands execute. Never grant broad access as a latency optimization.

Keep secrets out of transcripts, source, exported diagnostics, and application settings. Use supported credential storage and credential isolation. Verify whether native agents pass credentials to child tools; never assume safety from a process-scoped environment variable. Block untrusted execution when the required isolation cannot be established.

Sanitize untrusted terminal control sequences and markup so tool output cannot spoof approval prompts or manipulate the display/clipboard. Keep deliberate foreground-shell passthrough a separately disclosed boundary. YAV telemetry is off by default; show provider data-sharing boundaries, especially across two providers.

16. Usage, billing, and limits

Track each role separately and together: available input/output tokens, cache usage, provider-reported charges, quota indicators, retries, turns, and elapsed time. Record source, timestamp, and whether values are reported, estimated, cumulative, or unavailable.

Normalize cumulative counters without double-counting resumed sessions. Do not add overlapping token categories. Missing information is Unavailable, never zero. Distinguish subscription fees, included usage, purchased credits, and API charges; do not invent cash savings from unused subscription tokens.

Display the billing route before work. Price estimates need versioned rates and clear limitations. Never change accounts, buy credits, enable paid overage, or move to another provider without authorization.

Implement elapsed-time, repair-cycle, queue, and supported usage limits. Block YAV-controlled new turns after a reached limit, checkpoint incomplete work, and disclose in-flight or delayed-reporting overruns. Do not call an observed threshold a guaranteed cash cap or promise cancellation refunds.

17. Latency measurements and durable recovery

Measure console startup, local preparation, agent initialization, implementation, tool activity, review, tests, approval waiting, repair, apply, and total completion time. Distinguish overlapping versus sequential intervals; do not sum overlapping spans as elapsed time.

Show time to first useful action separately from time to an accepted result. If the provider does not expose queueing versus hidden reasoning versus inference time, label the combined interval Provider time rather than inventing a breakdown.

Set development targets—not promises—of an interactive prompt within one second on the documented reference machine and local command acknowledgement within 200 milliseconds, without waiting for network discovery. Measure actual results. Provider inference remains outside these local responsiveness targets.

Persist tasks, profiles, session IDs, events, candidate fingerprints, findings, test results, usage, and checkpoints with migrations and atomic transitions. Keep source snapshots/logs in protected local storage, outside tracked project source.

After a crash or ambiguous timeout, mark Needs Reconciliation. Check provider and workspace state before resubmitting; never repeat a possibly completed mutation blindly. Retry safe transient operations with bounded backoff and respect rate-limit cooldowns.

Checkpoint on exit and resume on the next launch. Do not imply work continues after the application exits unless a separately implemented and explicitly enabled service provides that capability. Provide retention controls, history, patch export, redacted diagnostics, and data deletion.

18. Benchmark the actual improvement

Create at least ten representative tasks covering small edits, bugs, tests, features, refactoring, multi-file behavior, and related follow-ups. Use trusted acceptance checks defined before running agents.

Compare YAV against the same two-model workflow in normal terminals, with identical model versions, effort, account routes, tools, permissions, project instructions, snapshots, and quality gates. Also compare `/optimization off` to isolate YAV’s supplemental changes. Report single-model baselines separately, never as an equivalent quality-controlled workflow.

Randomize order and repeat runs where feasible. Include cold and warm environments, failures, repairs, indexing/setup, validation, review, and application overhead. Separate active time and approval waiting while reporting total elapsed time.

Report success rate, regressions, matched-success timing, median/tail latency, usage, and available actual cost. Include failed-run consumption in cost per successful task. Evaluate provider speed and Adaptive mode separately because billing or reasoning configuration changes.

Do not invent savings or generalize a finite benchmark into guaranteed quality parity. Disable or narrow optimizations that worsen measured outcomes. Live benchmarks consume usage and require explicit authorization; ordinary tests use fixtures.

19. Implementation stages and acceptance tests

Stage 1: Deliver a working inline shell, local commands, project selection, prerequisite detection, one real adapter, streaming, approvals, cancellation, and history.

Stage 2: Add two distinct configured models, maximum-effort verification, separate reviewer context, immutable candidates, concurrent review/tests, structured findings, and bounded repairs. This is the core product milestone, not optional polish.

Stage 3: Complete dirty-workspace preservation, protected apply/undo, crash reconciliation, trustworthy usage, incremental preparation, session/environment reuse, provider-speed controls, and benchmark instrumentation. Keep Adaptive mode isolated and off by default.

Stage 4: Produce the portable self-contained Windows package and per-user installer, optional PATH registration/shortcut, documentation, clean-machine checks, and measured results. Do not require users to install the .NET runtime separately; package agent prerequisites only where licensing and provider guidance permit.

Test command parsing, multiline input, event framing, usage normalization, model/effort mismatches, quota exhaustion, unavailable reviewers, invalid review output, stale approvals, modified tests, and mutation during validation.

Test dirty Git repositories, non-Git snapshots, binary files, renames, Unicode/space-containing paths, conflict-aware apply/undo, interrupted runs, malicious terminal output, approval handling, and credential exposure boundaries. Verify cancellation leaves unrelated processes alive.

Exercise the real application in Windows Terminal, PowerShell, and CMD, including redirected/JSON output and foreground-shell return. A UI mock or Linux-only test does not prove Windows console integration works.
